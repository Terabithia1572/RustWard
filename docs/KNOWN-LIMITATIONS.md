# Known Limitations

Each limitation is a residual risk. "Accepted" requires written sign-off by the
security owner before Phase 9.

| ID | Limitation | Consequence | Mitigation | Status |
|---|---|---|---|---|
| L-01 | USB VID/PID and SCSI INQUIRY strings are not authenticated. | A device that reports an approved vendor (e.g. `SanDisk`) is allowed even if physically from another maker. Demonstrated by the `SPOOF0001` fixture test. | Physical control of media; VID mismatch shown as a warning; audit trail. Cannot be fixed in software. | Open — needs acceptance |
| L-02 | Some products report a controller/bridge vendor (`Generic`, `JMicron`, `ASMT`, `SMI`, `Phison`…) instead of the brand. | Such products of an approved brand are **denied**; they cannot be allowed at brand level without allowing every product using that controller. | Catalog rejects generic vendors. Any model-level exception must be a separate, explicit business decision. | Open |
| L-03 | New products of an approved brand that use a new INQUIRY vendor string are denied until the catalog is updated. | "Unseen devices work automatically" holds only while the brand keeps reporting a known vendor string. | Controlled offline catalog update with lab evidence. | By design |
| L-04 | Hardware-Encrypted USB identifiers are unknown. | Until inspected, every Hardware-Encrypted USB device is **denied** (default deny). If its vendor string is generic, brand-level allowlisting of Hardware-Encrypted USB is impossible. | Hardware inspection in Phase 2 (TEST-PLAN T-04..T-07). | Blocking |
| L-05 | Device Installation Restrictions do not re-evaluate already-installed devices. | Unauthorized drives connected before activation keep working. | Phase 10: `assess-installed` (CLI) and the **Uygulama Hazırlığı** page list every denied-but-installed storage device with **manual** Device Manager steps for an administrator. RustWard never uninstalls devices, removes PnP instances or uses retroactive rules. Verification scan after any manual cleanup. | Open — assessment implemented, cleanup is manual by design |
| L-06 | A local administrator can change or remove OS policy. | Protection assumes operators are standard users. | Separate admin accounts; audit; tamper-evident logs (not tamper-proof). | By design |
| L-07 | The `SCSI\` namespace is shared by UASP USB disks and internal disks. | An allow rule for a vendor also matches internal disks of that vendor; vendor padding is unconfirmed. | Instance-ID allow rules for internal disks; hardware verification. | Open |
| L-08 | USB CD/DVD and MTP/PTP devices are outside the DiskDrive rule. | Not blocked unless a scope decision adds their classes. Reported as `enforcement_gap`. | Scope decision required. | Open |
| L-09 | Preventing the DiskDrive class blocks new internal disks and VHD/VHDX mounts. | Maintenance needs an admin procedure. | Baseline instance-ID allow rules; documented maintenance window. | By design |
| L-10 | Windows 10 left mainstream support on 2025-10-14. | Unpatched OS weakens every control. | Confirm ESU or Windows 11 migration plan. | Open — owner decision |
| L-11 | Local logs can be altered by a sufficiently privileged administrator. | Logs are tamper-evident at best. | Hash chain + Windows Event Log; never claimed tamper-proof. | By design |
| L-12 | No enforcement exists in this build (`ACTIVATION_ENABLED = false`). | Running RustWard today protects nothing. | Every output and the dashboard banner say so; the UI labels decisions "SİMÜLE". | Current state |
| L-13 | No Windows-specific code has been executed: SetupAPI inventory, **the read-only policy reader (Phase 10)**, named pipes, impersonation/elevation checks, SCM service, Tauri on WebView2, MSI. | Defects may exist that Linux tests cannot reveal. | Type-checking (`host-typecheck`), Linux compile of the Tauri shell; **Phase 11: Windows-target compile, link and import scan on Linux (`scripts/windows-target-check.sh`, not native)**; full acceptance on the Windows VM with the prepared scripts (PHASE-11-NATIVE-VALIDATION.md). | DEFERRED by owner |
| L-14 | The SCM host has never run. The previous `windows-service`-based `scm.rs` was never compiled anywhere; it was replaced by a windows-sys host in `rustward-windows` that is type-checked on Linux and whose `unsafe` blocks are explicit and reviewed. | Start/stop/recovery behaviour under the SCM is unknown. | First acceptance step: build and start the service on the Windows VM. | DEFERRED |
| L-15 | Administrative actions require the desktop app to run elevated ("Run as administrator"); there is no in-app elevation prompt. | Operators may find admin actions failing with "elevated administrator required". | Server-side authorization is intentional; add an elevation helper or documented shortcut after acceptance. | Open |
| L-16 | Notifications are in-app only (window open); Windows toast notifications are not implemented. Event Log mirroring and `CM_Register_Notification` wake-ups are implemented but never executed on Windows. The event source + embedded message table are prepared in the installer draft (Phase 9A) but unverified. | A closed UI shows no notice; Event Log formatting and real-time detection are unproven. | Verify on the VM (WINDOWS-VM-ACCEPTANCE.md Stage D). | Partially resolved |
| L-17 | The initial policy is `config/policy.example.json` (`PC-01`); an administrator must rename each workstation in Settings after installation (versioned, audited). | Until renamed, five workstations report the same ID. | Installer property, or a mandatory first-run step. | Partially resolved |
| L-18 | `tauri build` with `webviewInstallMode = offlineInstaller` needs internet on the build machine (HEAD request to Microsoft each build; WiX download if not cached). | An air-gapped build machine cannot produce this MSI. | Connected build machine, or `fixedVersion` mode + pre-provisioned WiX (`OFFLINE-DEPLOYMENT.md` §3). | By design of Tauri |
| L-19 | Binaries and MSI are unsigned. | SmartScreen/AppLocker may block them; integrity relies on SHA-256 sums. | Code-signing process outside the repository. | Open |
| L-20 | The MSI service fragment (`packaging/wix/rustward-service.wxs`) is a draft. | Install, repair, upgrade and uninstall behaviour is unknown. | Build and test only on the acceptance VM. | DEFERRED |
| L-21 | The dev backend's database lives in the user temp directory and its identity is a synthetic administrator. | Acceptable only for development. | Compiled only with `debug_assertions` + `dev-backend`; release-mode test proves it is never selected. | By design |
| L-22 | ~~Restoring a backup replaces the audit table with the backup's history.~~ | — | Replaced in Phase 9A by a two-step, non-destructive restore that never touches the audit log (AUDIT-INTEGRITY.md). | Resolved (Phase 9A) |
| L-23 | Authorization failures are audited at most 20 per minute; further attempts are counted and reported with the next recorded one. | A flood is summarised rather than itemised. | Rate limit protects the audit log from exhaustion. | By design |
| L-24 | The local audit log is tamper-evident, not tamper-proof: an administrator can drop the append-only triggers, recompute the unkeyed chain, reset SQLite's sequence counter, delete backups and clear the Event Log. | Audit evidence depends on an out-of-database copy surviving. | Phase 9B: truncation/gap detection, daily `audit_checkpoint` mirrored to the Event Log, read-only `verify-checkpoint`; periodic export to write-once media (AUDIT-INTEGRITY.md §5a/§6). | Partially mitigated; by design (F-12) |
| L-25 | ~~The Event Log mirror cursor is in memory.~~ | — | Phase 9B: persisted cursor, ordered back-fill (max 1000, gap recorded as Event 1009), retry every tick; at-least-once delivery. Event Log delivery itself is unverified on Windows. | Resolved in logic (F-15) |
| L-26 | Pooled pipe servers (Phase 9B): status pipe 8 concurrent callers, admin pipe 4, 15 s idle timeout. A standard user can still occupy all 8 status slots by reconnecting. | The dashboard of other standard users can show "service unavailable"; the admin pipe and policy are unaffected. | Per-account slot limits could be added after VM measurements. | Mitigated, residual (F-13); verify on Windows (C18) |
| L-27 | ~~Pipe threads not joined at stop.~~ | — | Phase 9B: shutdown wakes the acceptor, answers in-flight requests and joins all threads within 3 s per pipe; incomplete shutdowns audited (Event 1010). | Resolved in logic (F-14); verify on Windows (C19) |
| L-28 | The service runs as `LocalSystem`. | More privilege than inventory, SQLite and pipes need. | Phase 9B prepared a virtual-account variant (service SID, SDDL builders, client owner check accepts the service SID, server-PID check). A future enforcement write path needs HKLM policy writes, which a virtual account cannot do. | Open, prepared (F-16); decide in VM step C16 |
| L-29 | Activation gates are implemented (`rustward-enforcement::activation`) but no activation path exists; several gates are hard-wired NotMet (`vm_validation`, undocumented registry values). | Enforcement cannot be enabled by configuration. | Intentional for Phase 9A; Stage F of WINDOWS-VM-ACCEPTANCE.md. | Current state |
| L-30 | The test runner (Vitest 3.2.7, tinypool 1.1.1) has published advisories; upgrading in the container failed with an npm 10.9.9 internal error. | Developer/build machine only; production dependencies: 0 vulnerabilities; nothing is shipped from the test toolchain. | Upgrade to Vitest ≥ 4.1.12 on the build machine and re-run all tests. | Open (F-21) |
| L-31 | Phase 10: read-only capture of the Restrictions key is **implemented** (`rustward-windows::policy_reader`, `KEY_READ` only) but **never executed on Windows**. The list-entry layout (subkey of numbered values) and the `*Retroactive` value names are not in the Policy CSP mapping table and are reported as **unresolved**; UBR comes from an undocumented value, so Windows 10 layering support is reported as unresolved (confirm with `winver`). | `existing_policy_compatible` can only be evaluated from a real capture; the plan's list layout is unconfirmed. | Checklist E1–E10 (`reg export` comparison, before/after identical); confirm the two unresolved items from documentation or a delivered image. | Partially addressed — unverified on Windows |
| L-32 | Phase 10 installed-device assessment uses the inventory's problem code 28 and driver service to decide "installed". Other states (for example a disabled device or a pending reboot) are reported as `unknown` and treated as installed (fail-safe). Only disk-class devices are assessed. | Some devices may be listed for manual review unnecessarily; non-disk storage (CD/DVD, MTP) stays out of scope (L-08). | Administrator review of the sanitized report before any manual step. | Open |
| L-33 | Mock policy backend tests (`tests/mock_policy_backend.rs`) prove the rollback and partial-state logic against an **in-memory** model of the registry only. | Real registry behaviour (ACLs, Group Policy refresh overwriting values, WOW64 views) is not exercised. | Stage F, separately authorized, on physical hardware. | Open — by design until Stage F |
| L-34 | Phase 11 (R-11-1): an internal or boot disk can get a new instance ID without a disk being added (controller mode AHCI/RAID/VMD, port, storage driver stack, cloning, VM controller type). The new devnode is not in the baseline allow list and falls under the DiskDrive prevent; the effect during boot is unverified. | A firmware or hardware change after activation could make a workstation unbootable. | Suspend before any firmware/controller/disk change; re-enumeration test plus WinRE recovery rehearsal in Stage F. | Open — Stage F prerequisite |
| L-35 | Phase 11 (R-11-3): the Tauri MSI template declares `InstallerVersion="450"` while the data-folder ACL uses `MsiLockPermissionsEx` (Windows Installer 5.0). | The `%ProgramData%\RustWard` ACL may not be applied as intended. | Checklist C3 (the Stage C script records the SDDL); fall back to a service-side ACL check if it fails. | Open — verify on Windows |
